# Retry Routing: Second-Best Interpretations and Exhaustive Retry Protocol

Wave 1 research. Companion to `contrastive-routing.md` and `abstention-policy.md`.

**Revision note (2026-03-21 evening):** Updated from a two-attempt architecture to an exhaustive iterative retry loop per live-runtime policy. The canonical semantic analysis (which retries are semantically justified) is unchanged; the live policy section is corrected to reflect that the runtime never stops at `unresolved` due to rejection — it continues until the task universe is exhausted.

---

## Two Distinct Layers — Do Not Conflate

This document maintains a strict separation between two concerns:

**Layer 1 — Canonical semantic truth**
What the prompt actually IS and what it could plausibly be reinterpreted as. This research is ground truth for corpus labeling, training data, and human audits. A prompt that canonically has no semantically valid second interpretation STAYS unresolved in the corpus regardless of what the live runtime does.

**Layer 2 — Live exhaustive retry policy**
After a runtime rejection, the classifier is re-prompted with the rejected task excluded. The runtime loops until it either dispatches an eligible task or the full task universe is exhausted. The runtime NEVER produces `unresolved` as a consequence of rejection — it always advances to the next candidate. This is a live dispatch policy, not a semantic claim.

A task that has "no semantically valid second-best" (Layer 1) is NOT the same as "the runtime stops here" (Layer 2). They diverge exactly for the semantically isolated tasks (12, 13, 28, etc.): canonically no justified neighbor exists, but the live runtime continues forcing different task IDs anyway. Those forced dispatches are live policy retries, not canonical semantic matches.

---

## Architecture Contract

**Iterative/exhaustive retry loop:**

```
attempt-N → resolved(taskId=X, inputJson=...)
          → runtime checks eligibility of X
          → eligible: dispatch X — done
          → not eligible: add X to exclusion set → attempt-(N+1)

attempt-(N+1) → prompt includes all previously excluded task ids
             → resolved(taskId=Y, Y ∉ exclusion set, inputJson=...)
               → eligible: dispatch Y — done
               → not eligible: add Y to exclusion set → attempt-(N+2)
             → OR: universe exhausted (all 30 tasks in exclusion set)
               → runtime logs "universe exhausted" — final fallback TBD by runtime policy
```

**Critical constraints (preserved from before):**
- Each attempt must never return a `taskId` already in the exclusion set.
- The one-task / one-strategy interface is preserved at every attempt: each attempt produces a single `resolved` task + `inputJson`.
- The rejection context injected per attempt remains minimal (see below).
- **Canonical corpus records attempt-1 as the semantic ground truth.** Subsequent attempts are runtime policy choices, logged separately.

**What changes from the two-attempt model:**
- There is no "attempt-2 must return `unresolved`" constraint. The classifier always tries to find the next eligible task.
- `unresolved` is still a valid output from any attempt — but it is generated by the classifier's own semantic judgment (no task fits), NOT forced by the runtime rejection mechanism.
- The exclusion set grows with each rejected task; the classifier sees the full cumulative list each time.

## Minimal Rejection Context Per Attempt

Append this block at the end of the AGENTS.md classifier prompt for every retry attempt:

```
## Retry instruction
The following task(s) have already been handled and are not available: {comma-separated exclusion set}.
Choose a DIFFERENT task interpretation from the remaining tasks.
Do not return any of the excluded task ids.
```

This is the complete injection. Nothing else. Do not include:
- Why tasks were rejected (already-perfect, non-eligible — live-policy details)
- Any hint about what the "correct" next interpretation is
- Score or leaderboard data
- The number of attempts already made

The exclusion set grows monotonically. By attempt-K, it lists all K-1 previously rejected task IDs.

## Three-Tier Retry Classification

Every retry, across every cluster, falls into one of three tiers. The tier determines how much confidence to place in the dispatch and whether the corpus should record it as a meaningful semantic match.

### Tier A — Semantically Supported Retry
The prompt genuinely supports the new interpretation. The second-best task is a real reading of the same prompt text, not a stretch. The strategy is likely to score meaningfully.

Corpus treatment: record as "semantically valid alternate interpretation — second choice".

| Rejected → Retry | Condition | Notes |
|---|---|---|
| 20 → 16 | Text supplier invoice fields present | Drop attachment; same semantic content |
| 21 → 24 | Prompt lists specific error values | Same strategy family, different variant |
| 24 → 21 | Mirror of above | |
| 25 → 17 | Always | Drop fee step; payment core is the same |
| 29 → 15 | Hours + rate + activity present | 15 is a true subset of 29 |
| 19 → 06 | Identity fields extractable | Drop contract details; identity core unchanged |

### Tier B — Semantically Fragile Retry
The new interpretation requires suppressing a signal that was present in the prompt, or elevating a weak signal to primary status. The strategy may score but the reinterpretation is not a natural reading. Risk of wrong API side effects.

Corpus treatment: record as "forced reinterpretation — not a natural reading, runtime policy".

| Rejected → Retry | Condition | Fragility reason |
|---|---|---|
| 08 → 09 | Product catalog refs present | "send" signal must be suppressed |
| 09 → 11 | Payment language present but weak | Payment step was de-prioritized in attempt-1 |
| 11 → 09 | Drop payment step | Payment was part of the explicit prompt |
| 10 → 18 | Prompt used "reverse" without "credit note" | Credit-note language absent but reversal language is ambiguous |
| 18 → 10 | No "bank returned" signal, invoice-centric framing | Assumes credit-note intent from reversal framing |
| 16 → 20 | PDF attachment present | Valid only if PDF is genuinely present |
| 06 → 19 | Attachment present | Requires inferring contract details from minimal prompt |
| 15 → 29 | Extra lifecycle signals present | Assumes fuller scope was intended |
| 29 → 14 | Fixed-price language absent from 29 prompts | Very weak; 29 prompts never have milestone billing |
| 14 → 05 | Drop billing step | Billing was the stated objective |
| 17 → 25 | Overdue + fee + partial amounts explicit | Only Tier B if the fee/partial signals are present but were not attempt-1's trigger |
| 27 → 17 | Invoice turns out to be NOK on re-reading | Very weak; 27 prompts always have explicit currency |

### Tier C — Forced Policy Retry (runtime only, not canonical truth)
No semantically valid reinterpretation exists. The canonical semantic analysis is exhausted. The live runtime continues anyway — it excludes the rejected tasks and selects the next closest available task by whatever remaining signal exists, which may be very weak or coincidental.

**This is a live dispatch decision, not a semantic claim.** Do NOT record Tier-C retries as valid alternate interpretations in the canonical corpus. Log them as "no-semantic-neighbor, forced by exhaustion policy".

Tier-C tasks — tasks for which canonical semantics offer no justified neighbor:

| Task | Reason canonical semantics are exhausted |
|---|---|
| **12** (payroll) | No other task processes salary + bonus for an existing employee |
| **13** (travel expense) | No other task registers per-diem + cost categories + delivery for a trip |
| **28** (expense analysis + internal projects) | No other task compares monthly ledger aggregates and creates internal projects |
| **07** (accounting dimension + voucher) | Dimension creation is unique; no semantic neighbor among other tasks |
| **03** (create departments) | Atomic creation task; no semantic overlap with billing/payment/project tasks |
| **04** (create product) | Same as 03 |
| **01** (create customer) | Entity creation with distinct required fields |
| **02** (create supplier) | Entity creation with distinct required fields |
| **27** (FX payment) | FX agio bookings have no domestic-payment substitute; also currently unsupported |
| **23**, **26**, **30** | Unknown task families; no evidence of semantics |
| **22** (receipt voucher), after 16 rejected | Receipt and supplier invoice differ structurally; forced reinterpretation is very likely wrong |

**What the live runtime does for Tier-C tasks:** After canonical semantics are exhausted, the exclusion set grows and the classifier is re-prompted. It will produce SOME `resolved` output from the remaining tasks — likely whatever is nearest in surface vocabulary. That dispatch is a last-resort policy bet, not a semantic match. The runtime may choose to stop if it detects the classifier returning low-confidence or clearly mismatched resolutions, but that stop logic is a runtime implementation detail, not a routing research rule.

**Critical:** Never allow Tier-C forced dispatches to feed back into classifier training or corpus labeling. They are noise for semantic purposes.

## Decision Loop for the Live Classifier

```
Receive: prompt + exclusion_set (grows with each retry)

Step 1: Apply full contrastive routing (contrastive-routing.md) over
        tasks NOT in exclusion_set.
        → Best match = X (not in exclusion_set)?

Step 2: Determine tier.
        → Tier A (semantically supported)? → emit resolved(X, inputJson)
        → Tier B (fragile but possible)? → emit resolved(X, inputJson),
          runtime logs tier=B warning
        → No match at all? → emit unresolved(code="no-task-match")
          (this is the classifier's own semantic judgment, not a forced stop)

Step 3: Runtime receives resolved(X):
        → X eligible? dispatch X — done.
        → X not eligible? add X to exclusion_set → go to Step 1.

Step 4: Universe exhausted (exclusion_set == all 30 tasks):
        → Runtime logs "universe exhausted" → apply final fallback policy
          (runtime implementation detail, out of scope for this document).
```

**Key difference from the old two-attempt model:** Step 3 loops. The classifier is not asked "can you return `unresolved` to stop?". It is asked to always find the next best task from the remaining universe. Only the classifier's own semantic judgment (Step 2 "no match at all") produces `unresolved` — and even that gets retried at the next loop iteration with a broader exclusion set.

## Canonical Corpus Logging (unchanged)

Each retry attempt must be logged separately. The canonical corpus records:

| Field | Value |
|---|---|
| `classificationAttempt` | 1, 2, 3, … |
| `taskId` | The task returned at this attempt |
| `tier` | A / B / C (from the tier classification above) |
| `rejectedBefore` | List of task IDs excluded at this attempt |
| `canonicalGroundTruth` | Always attempt-1's `taskId` |
| `dispatchedTask` | The first eligible task that was actually run |

**Rule:** `canonicalGroundTruth` is always attempt-1. It is NEVER overwritten by a later retry. If a future audit asks "what task was this prompt?", the answer is always attempt-1, regardless of what was dispatched.

Tier-C dispatches must be tagged as `tier: "C"` and excluded from any semantic analysis, training set construction, or routing quality measurement. They are pure policy noise for semantic purposes.
